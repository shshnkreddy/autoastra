# AutoAstra

Give a coding agent a problem, a fitness function, and a time budget. AutoAstra runs one agent session in Docker. The agent edits `final_solution.py`, scores each attempt, and records what it learned. You get the selected solution and an experiment ledger that shows how the agent arrived at it.

[Quickstart](#quickstart) · [Model access](#model-access) · [Run settings](#run-settings) · [Create a task](#create-a-task)

## Quickstart

The bundled **affine** task asks the agent to infer a linear rule from examples and implement `predict(xs)`. Its score is the mean absolute prediction error. A perfect solution scores zero.

### 1. Install and preview the demo

Use Python 3.11 or newer. The preview runs with Python alone and lets you read exactly what the agent will see.

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install git+https://github.com/shshnkreddy/autoastra.git

autoastra preview tasks.affine:task --output previews/affine --print-to previews/affine.md
```

Open `previews/affine.md` for the task tree, instructions, and starter files.

### 2. Start a run

On a Linux host with Docker available to your non-root user, configure one of the providers under [Model access](#model-access). With a configured Codex subscription, run:

```sh
autoastra run tasks.affine:task --output runs/affine
```

The demo allows **10 minutes and 20 evaluations**. Docker pulls `python:3.12-slim` on first use. Choose a new output directory for each run. [Docker installation](https://docs.docker.com/engine/install/) · [Linux user setup](https://docs.docker.com/engine/install/linux-postinstall/)

### 3. Inspect the result

```sh
autoastra result runs/affine
```

This prints the selected source and its recorded development fitness, then writes a plot of the official evaluations.

| Under `runs/affine/` | What you’ll find |
| --- | --- |
| `task/workspace/final_solution.py` | The selected revision after a successful run |
| `task/ledger/ledger.md` | A readable history of hypotheses, changes, scores, and conclusions |
| `task/ledger/ledger.jsonl` and `task/ledger/snapshots/` | The original events and the source revisions they refer to |
| `result.json` | Run status, stop reason, usage, and selection |
| `fitness.png` | Fitness by evaluation attempt, generated by `autoastra result` |

To follow a run while it is active, use `tail -f runs/affine/.runtime/ledger.jsonl`. If every evaluation fails, `result.json` records that there is no selected solution.

## Model access

Choose one provider on the **execution host**. Install its native Linux CLI there, or include it in the task image. Keep credentials in the launch environment or a dedicated login profile.

| Provider | Agent CLI | Add to `autoastra run` |
| --- | --- | --- |
| ChatGPT subscription | `codex` | Defaults to Codex. Use `--model` to choose a model. |
| OpenRouter | `codex` | `--provider openrouter --model PROVIDER/MODEL` |
| Anthropic | `claude` | `--provider anthropic --model sonnet` |
| OpenCode | `opencode` | `--provider opencode --model provider/model` |

<details>
<summary><strong>Codex with a ChatGPT subscription</strong></summary>

Install the native Codex CLI and sign in with a dedicated profile that the runner can mount into the development container.

```sh
export AUTOASTRA_CODEX_HOME="$HOME/.local/share/autoastra/codex"
mkdir -p "$AUTOASTRA_CODEX_HOME"
CODEX_HOME="$AUTOASTRA_CODEX_HOME" codex -c 'cli_auth_credentials_store="file"' login
CODEX_HOME="$AUTOASTRA_CODEX_HOME" codex login status
```

On a headless server, add `--device-auth` to the login command. To reuse an existing signed-in profile, set `AUTOASTRA_CODEX_HOME` to its directory or pass `--codex-home`. Keep the native installation and its companion tools together when selecting a binary with `--codex-binary`. [Codex CLI](https://developers.openai.com/codex/cli/) · [Sign-in guide](https://developers.openai.com/codex/auth/)

</details>

<details>
<summary><strong>OpenRouter through Codex</strong></summary>

Install the native Codex CLI. Export your key in the launch shell and choose a model that supports coding tools through OpenRouter’s Responses API.

```sh
export OPENROUTER_API_KEY="your-key"
autoastra run tasks.affine:task --provider openrouter --model PROVIDER/MODEL --output runs/affine-openrouter
```

[OpenRouter API keys](https://openrouter.ai/settings/keys) · [Codex setup](https://openrouter.ai/blog/tutorials/codex-cli-openrouter/)

</details>

<details>
<summary><strong>Claude Code with Anthropic</strong></summary>

Install Claude Code. For API billing, export `ANTHROPIC_API_KEY`. For a subscription, run `claude setup-token` and export its value as `CLAUDE_CODE_OAUTH_TOKEN`. The API key takes precedence when both are set.

```sh
autoastra run tasks.affine:task --provider anthropic --model sonnet --output runs/affine-claude
```

To select a specific native executable, pass `--claude-binary`. Use `autoastra preview --provider anthropic` with the usual task and output arguments to see the Claude-specific `CLAUDE.md` instructions. [Claude Code setup](https://code.claude.com/docs/en/setup) · [Authentication](https://code.claude.com/docs/en/authentication)

</details>

<details>
<summary><strong>OpenCode</strong></summary>

Install OpenCode and export the key for your chosen backend. AutoAstra supports `OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, and `OPENCODE_API_KEY`. For example, with an Anthropic key:

```sh
autoastra run tasks.affine:task --provider opencode --model anthropic/claude-sonnet-4-6 --output runs/affine-opencode
```

Use `--opencode-binary` to select a specific native executable. [OpenCode CLI](https://opencode.ai/docs/cli/)

## Run settings

Each task supplies defaults. Override individual settings with `--run-config path/to/config.json`. Explicit CLI flags take precedence. The effective settings are saved in `task/context/run_config.json`.

| Setting | Example | Effect |
| --- | --- | --- |
| Budgets | `--time-seconds 600 --max-evaluations 20` | Limits each run independently. Startup time and failed evaluations count. |
| Token usage | `--max-tokens 100000` | Stops on reported usage, including cached input. An in-flight request can exceed the limit. |
| Parallel seeds | `--seeds 0 1 --jobs 2` | Starts two independent sessions with separate output directories. |
| Final selection | `--selection best-fitness` | Restores the best officially scored revision by default. Use `model` for the agent’s selection. |
| CPU and memory | `--cpus 2 --memory-mb 4096` | Sets container resources. The run defaults are one CPU and 2 GiB. |
| GPUs | `--gpus 1` or `--gpu-device 0` | Exposes the requested GPUs to the task containers. |

GPU runs need compatible drivers, the NVIDIA Container Toolkit, and a task image with the required CUDA libraries. [Docker GPU setup](https://docs.docker.com/engine/containers/gpu/)

## Inside the sandbox

The agent works in one persistent development container. For each official score, AutoAstra starts a temporary offline container using the same task image. It loads a frozen copy of the submission, calls the fitness function, and returns the score. The evaluator and submission share a Python process, so scoring assumes a cooperative submission.

```text
task/
├── AGENTS.md                 # CLAUDE.md for Claude Code
├── bin/                      # fitness-eval, experiment-ledger, lifetime
├── context/                  # Read-only task spec, fitness API, and run settings
├── ledger/                   # Experiment history and source snapshots
└── workspace/                # Editable
    ├── final_solution.py
    └── scratch.py
```

The agent uses `experiment-ledger` to register a revision and its hypothesis, `fitness-eval` to score it, and `lifetime` to check its remaining budget. The ledger links each score to the registered source. The finished run retains the workspace and ledger after the containers exit.

To check a task image directly, run a command in a standalone sandbox:

```sh
autoastra sandbox tasks.affine:task --output runs/sandbox-check -- python -c "print('Sandbox ready')"
```

## Create a task

A task combines the instructions the agent reads, the fitness function that scores a submission, and the Docker image that supplies its dependencies. Save this example as `my_task.py` in your project folder.

```python
import runpy

from autoastra import Task


def evaluate(solution_path, *, split, seed):
    predict = runpy.run_path(str(solution_path))["predict"]
    inputs = [-2, 4, 8]
    expected = [2 * x + 1 for x in inputs]
    actual = predict(inputs)
    return sum(abs(a - b) for a, b in zip(actual, expected, strict=True)) / len(inputs)


task = Task(
    task_spec={
        "name": "linear_rule",
        "description": "Infer the affine rule from (0, 1), (1, 3), and (3, 7).",
        "solution_interface": "Implement predict(xs) in final_solution.py. Return one number per input.",
        "metric": "mean_absolute_error",
        "direction": "minimize",
    },
    fitness_fn=evaluate,
    image="python:3.12-slim",
    run_config={"time_seconds": 600, "max_evaluations": 20},
)
```

Use `module:object` to select a task. Here, `my_task:task` refers to the `task` object in `my_task.py`. You can also point to an installed package, for example `my_lab.problems:task`.

```sh
autoastra preview my_task:task --output previews/linear
autoastra run my_task:task --output runs/linear
autoastra result runs/linear
```

**Task dependencies.** Build an image on the execution host (`docker build -t my-task:v1 .`) or use a registry reference. Set `Task.image` to that name. AutoAstra uses a local image when available and pulls it otherwise. For a private registry, run `docker login` on the host first. Include both `python` and `python3` in the image. Import evaluator-only dependencies inside the fitness function so the host can load the task.

**Python API.** You can also run the task directly from Python:

```python
from autoastra.autoresearch import run
from my_task import task

result = run(task, "runs/linear-python")
print(result["solution"])
```
